## 1. 目的

日本人英語学習者が「英語を聞き取れる」ようになるための、スマホで使える学習ツールを作る。
**学術的な研究で効果が示されている方法を中心に構成し、各機能に根拠と根拠の強さを明記する。**

## 2. 基本方針・制約

| 項目 | 方針 |
|---|---|
| 費用 | 有料サービス・有料APIは使わない |
| 利用端末 | スマホ（iPhone / Android） |
| 形式 | PWA（ブラウザで動作し、ホーム画面に追加できるWebアプリ） |
| 公開 | GitHub Pages（無料プラン・公開リポジトリ） |
| 音声 | 無料のオープンソースTTSで事前生成した音声を基本とし、端末内蔵TTSで補完 |
| 外部送信 | 学習データ・入力内容を外部サービスへ送らない（音声認識APIなど外部送信を伴う機能は採用しない） |
| アカウント | 不要。学習記録は端末内に保存 |
| 根拠 | 機能ごとに根拠を記載。根拠の弱いものはそう明記する |

## 3. 根拠の強さの表記

| 記号 | 意味 |
|---|---|
| ◎ | 複数の査読付き研究で効果が確認されている |
| ○ | 研究で効果の報告があるが、条件付き・小規模 |
| △ | 研究上の直接的な根拠は弱い（診断・補助として使う） |
| ※ | 今回の調査では未確認の一般的知見（実装前に確認が望ましい） |

## 4. 機能一覧

### 4.1 聞き分け訓練（HVPT）【最優先・MVP】

**根拠：◎**
- High Variability Phonetic Training（HVPT）。複数話者・複数の音環境の自然音声で訓練すると、日本人の /r/–/l/ 識別が改善し、未訓練の語にも般化、3か月後も保持、発音も改善（Logan, Lively & Pisoni 1991；Lively et al. 1993, 1994；Bradlow et al. 1997, 1999）。
- 訓練方式の違いにかかわらず、日本人成人の /r/–/l/ 識別が平均15〜20ポイント向上（Iverson, Hazan & Bannister 2005）。
- 1回10分×6週間の授業内訓練では /r/–/l/ に変化なし（Ueda & Hashimoto）→ **訓練量の確保が重要**。Bradlow らは合計15〜22.5時間。

**仕様**
- 形式：単語の音声を1つ聞き、2択（例：`right` / `light`）で答える（2AFC）。
- 回答直後に正誤を表示し、正解の音声と不正解側の音声を聞き比べられる。
- 毎回ランダムに話者を変える（事前生成した多話者音声を使う）。
- 対象の音素は語頭・語中・子音連結・語末など、複数の位置に含める。
- 1セッション約10〜15分。累計の訓練時間を記録・表示し、目標（例：15時間）までの進捗を示す。

**対象とする音の対立**
| 対立 | 例 | 根拠 |
|---|---|---|
| /r/–/l/ | right / light | ◎ |
| /b/–/v/ | berry / very | ○（Ueda & Hashimoto） |
| /s/–/θ/ | sink / think | ○（Ueda & Hashimoto） |
| /z/–/ð/ | breeze / breathe | ※ |
| /f/–/h/ | fall / hall | ※ |
| /æ/–/ʌ/–/ɑ/ | cap / cup / cop | ※ |
| /i/–/ɪ/ | sheep / ship | ※ |
| /u/–/ʊ/ | pool / pull | ※ |
| /s/–/ʃ/ | see / she | ※ |
| 語末子音の有無 | bat / batter など | ※ |

**解説ページ（聞き取りのコツと口の形）**
- 根拠：△（発音の仕組みは一般的な音声学の知見。解説を読むだけで聞き取りが伸びるという研究上の根拠は限定的なので、訓練の補助として位置づける。HVPT の総説では、識別訓練の直後に発音練習をすると発音面の効果を補える可能性が指摘されている）
- 内容：日本語との違い、聞き取りのコツ、口と舌の形（横から見た模式図。ふだんの位置から発音の形へ動くアニメーション。動きを減らす設定の端末では静止図）、例の音声（押すたびに違う話者）

**般化テスト**
- 訓練に使わない「テスト専用の話者」と「テスト専用の単語」を用意し、事前・事後テストで使う（研究と同じ評価方法）。

### 4.2 書き取りによる弱点診断（ディクテーション）

**根拠：△**（学習法としての効果を直接示す研究は今回の調査で見つからず。聞き取れない箇所を見つける診断として使う）

**仕様**
- 短い文を聞いて入力する。再生回数・速度を記録する。
- 原文と入力を単語単位で照合し、誤りを次のように分類する（自動判定は簡易的なもの）。
  | 分類 | 判定の目安 |
  |---|---|
  | 弱形の聞き落とし | 機能語（a, the, to, of, and, can など）の脱落・誤り |
  | 連結・変化 | 単語の境界での誤り（例：`want to` → `wanna` 由来の誤り） |
  | 未知語 | 学習者レベルの語彙範囲外の語 |
  | 音素の混同 | 4.1 の対立に該当する置き換え（例：`light` → `right`） |
- 分類結果に応じて、4.1・4.3・4.4 の該当練習へ誘導する。

### 4.3 シャドーイング

**根拠：○**
- 日本人学習者で音素知覚が向上。ただし聴解テストの得点向上は**初級者のみ**（Hamada 2016）。
- ボトムアップ処理（音声知覚）の強化を通じて効果が出ると考えられている（門田 2007 など）。
- 他の活動（語彙学習など）と組み合わせると効果が高い。
- 効果は学習者の動機づけ・自信に左右される（Hamada 2015）。

**仕様**
- 手順：①内容理解（スクリプトと和訳を確認） → ②スクリプトを見ながら音声に合わせて読む → ③スクリプトなしでシャドーイング。
- 速度は 0.7〜1.2 倍で変更可能。
- 任意で自分の声を録音し、元の音声と聞き比べる（録音は端末内のみに保存し、外部へ送らない）。
- 自動採点は行わない（無料の音声認識は外部送信を伴う場合があるため）。

### 4.4 音の変化（連結・弱形・脱落）の学習

**根拠：○**（明示的に指導すると効果があるという報告：Hahn；Abe 2015 など。小規模）

**仕様**
- ルールごとの短い解説と例文音声：連結（`pick it up`）、弱形（`to`, `can`, `and`）、脱落（`next day`）、同化（`did you`）、/t/ のはじき音（`water`）など。
- 例文ごとに「ゆっくり・はっきり」と「自然な速さ」の2種類の音声を聞き比べる。
- 確認問題で終える（4.2 と同じ形式）。

**注意**：TTSは音の変化の再現が不自然な場合がある。音声を作るときに確認し、不自然なものは採用しない。

### 4.5 多聴

**根拠：○**（対照群より聴解力が大きく伸びたという研究がある。目的は自動化・流暢さ）

**仕様**
- レベルに合った音声教材（VOA Learning English、LibriVox など）の一覧を表示する。
- 聞いた時間・本数を記録する。
- 「どのくらい理解できたか」を自己評価で記録する（理解度が低い教材が続いたらレベルを下げるよう提案する）。

### 4.6 語彙（補助）

**根拠：◎**（聞いた語の95%が既知なら理解できる。必要語彙は約2,000〜3,000語族：van Zeeland & Schmitt 2013）

**仕様**
- 教材の語を高頻度語リストと照合し、レベル内の語でカバー率95%以上になる教材を優先する。
- 教材に出てくるレベル外の語を、事前に音声付きで確認できる。
- 頻度リストの候補：NGSL（New General Service List、CC BY-SA 4.0 ※要確認）

## 5. 学習者レベル

学習者が自分で選ぶほか、最初に簡単な診断テスト（4.1・4.2 の短縮版）で判定することもできる。いつでも変更できる。

| レベル | 目安 | 語彙範囲 | 速度 | 練習の比重 |
|---|---|---|---|---|
| 1 | 入門 | 上位1,000語 | 0.7〜0.8倍 | 聞き分け訓練＋シャドーイング |
| 2 | 初級 | 上位2,000語 | 0.8〜0.9倍 | 聞き分け訓練＋シャドーイング |
| 3 | 初中級 | 上位3,000語 | 0.9〜1.0倍 | 聞き分け訓練＋書き取り＋音の変化 |
| 4 | 中級 | 上位4,000語 | 1.0倍 | 書き取り＋音の変化＋多聴 |
| 5 | 中上級 | 4,000語超 | 1.0〜1.2倍 | 多聴＋書き取り |

※比重の根拠：シャドーイングは初級者で効果が出やすい（Hamada 2016）。中級以上は自動化（多聴）を重視。レベルの区切り自体は設計上の仮置き。

## 6. 音声

### 6.1 音声の用意

| 用途 | 音声 | 理由 |
|---|---|---|
| 聞き分け訓練 | Piper（`libritts_r` モデル、約900話者）で事前生成 | HVPTの「多くの話者」を無料で実現できる |
| 音の変化・書き取り・シャドーイング | Piper または Kokoro（約50声）で事前生成 ＋ VOA・Tatoeba の人間の音声 | 自然さを確保する |
| 多聴 | VOA Learning English、LibriVox（人間の音声） | 長い自然音声 |
| 補完（任意の文の読み上げ） | 端末内蔵TTS（Web Speech API） | 無料・外部送信なし |

### 6.2 根拠の限界と対策
- HVPT研究の多くは人間の自然音声を使っている。TTS音声で同等の効果が出るかの直接の根拠は少ない（Iverson ら 2005 は自然音声でなくても同程度の効果を示唆したが、暫定的な結果）。
- 対策：人間の録音（Mozilla Common Voice：CC0 など）を一部に混ぜる。事前・事後テストで効果を実測する。

### 6.3 音声生成の環境（PC側）
- 構築済み（2026-10-12）：
  - 既存の Python 3.12.10 から、作業フォルダ内に専用環境 `.venv` を作成
  - `.venv` に `piper-tts` 1.8.0 と `soundfile` 0.14.0 を導入（ユーザー許可済み）
  - 音声モデル `voices/en_US-libritts_r-medium.onnx`（約75MB、904話者、22,050Hz）をダウンロード
  - 動作確認：単語1語あたり約0.5秒・約5KB（MP3）。生成は高速
- `.venv` と `voices/` は公開しない（`.gitignore` で除外する）。
- Kokoro は必要になった時点で、改めて許可を得てから導入する。

## 8. データ保存

- 学習記録（正答率、訓練時間、誤りの分類、レベル）は端末内（IndexedDB）に保存する。
- 機種変更やバックアップのため、JSON形式で書き出し・読み込みできるようにする。
- 学習記録をサーバーやクラウドへ送る機能は持たない。

## 9. 効果測定（聞き取り力のカルテ）

2026-10-12 の改善指示書（docs/english_listening_claudecode_improvement_plan.md）に基づき改訂。計算は app/metrics.js、テストは tests/metrics.test.js。

### 9.1 原則
- 総合点は作らない。指標ごとに「何を、どの条件で測ったか」を表示する。
- 練習した問題・初めての声・初めての単語を分ける（練習問題への慣れと、初見の音声への転移を区別する）。
- 問題数（例：17/20）と 95% の幅（Wilson の信頼区間）を必ず表示する。
- 差はパーセントポイントで表示する（60%→75% は +15 ポイント。相対では +25%）。
- データがない指標は 0% ではなく「未測定」と表示する。
- 表示するのは「このアプリのテスト指標の変化」であり、英語のリスニング力全体の改善とは表現しない。

### 9.2 指標の定義
| 指標 | データ元 | 条件 |
|---|---|---|
| 練習中の正答率 | 訓練の回答（50問ずつの区切り。最初と最新） | 訓練した単語 × 訓練で使う声。答えを見た直後の問題を含む |
| 初めての声 | テストの「訓練した単語」20問 | 訓練した単語 × 訓練に使わない声 |
| 初めての単語 | テストの「初めての単語」20問 | 訓練に使わない単語 × 訓練に使わない声 |
| 単語の強勢（同じ3区分） | 強勢の訓練・テスト | 同上（チャンスレベルは音節数から算出） |
| 書き取り・初めての文 | 初めて出題された文（10文ずつ） | 単語正解率。現在のレベルのみ。同じ文の単語は相関するため幅は目安 |
| 書き取り・前に出た文 | 2回目以降の文 | 文を覚えた効果を含む |
| 音の変化の確認問題 | 各レッスンの初回と最新 | 毎回同じ問題（訓練した問題のみ） |
| 内容理解 | なし | 未測定（テスト未実装） |
| 多聴の実績 | 多聴の記録 | 学習量であり、能力の指標ではない |

### 9.3 判定の文言
- 1回のみ：「初回の測定です。変化はまだ分かりません」
- どちらかが 20 問未満：「問題数が少ないため、変化は判断できません」
- 初回と最新の 95% の幅が重なる：「差は誤差の範囲かもしれません」
- 重ならない：「誤差の範囲を超えて上がって／下がっています」（有意差の検定ではない）

### 9.4 テストの種類と保持テスト
- 事前：最初のテスト／事後：前回のテスト以降に訓練した／遅延：最後の訓練から14日以上たち、その間訓練していない／再テスト：それ以外。
- 最後の訓練から 2 週間後・4 週間後を保持テストの目安として表示（通知はしない）。
- テストの記録に音声の版（audioVersion）を残し、版の違うテストは比較・グラフに含めない。

### 9.5 次の練習の候補
記録から機械的に出す候補であり、診断ではない（例：練習中は高いが初めての単語が低い → 慣れの可能性、テストで確認）。

## 9A. 教材・音声の品質保証

- `tools/audit.py`：音声の欠落・読み込み不可・無音・音割れ、訓練用とテスト用の分離、テストでの繰り返し、ペアの長さだけで正答できるか、発音記号・強勢ラベル・注記の位置を点検。`--asr` で PC 内の音声認識（faster-whisper base.en）による確認を追加（単語は2択の候補を与えて認識、文は原文と比較、文の強い語は語の長さ×音量で簡易推定）。結果は qa/audit_report.md・qa/audit.json。
- 自動確認の「不一致」は「要確認」であり、誤りと断定しない。未確認の項目は未確認と表示する。
- 人による確認：qa/review.html（明らかな不具合のみを判断。英語の正誤は判断しない）。結果は qa/human_review.json。
- 聞き分けの音声 v2（2026-10-12）：v1 は /s/–/θ/ で /s/ の語が 95% の割合で長く、長さだけで正答できた。v2 は同じ話者のペアを平均の長さにそろえ、それぞれ独立に ±15% ばらつかせて合成。長さだけでの正答率は 52〜57%（チャンス 50%）。実際の英語にある長さの違いも消える点はトレードオフ。
- 自動テスト：`tools/run_tests.py` が tests/index.html を PC 内の Edge（画面なし）で実行（採点・指標の計算・保存の互換性・主要画面の表示）。

## 9B. 声の性別と、外部素材のアプリ内再生（2026-10-12 追加）

- 文の教材（書き取り・シャドーイング・聞き読み・音の変化の確認問題・文のリズム）の声を、女性2・男性2 にした（v1 は 3 声とも男性だった）。音声モデルに性別の情報はないため、声の高さ（中央値 F0：165Hz 以上を女性らしい声と判断）で候補を絞り、PC 内の音声認識で最も聞き取りやすい声を選んだ（tools/voice_pitch.py、tools/pick_voices.py、data/voices.json）。音の変化の例・ゆっくり版・チャンツなどの 1 声の教材は従来の男性の声のまま。聞き分け訓練の 26 声には女性らしい声が約 7 声含まれる。
- 多聴の VOA・BBC・TED・LibriVox をアプリ内で再生できるようにした。配信元の多くはウェブページから一覧（RSS）を直接読ませないため、tools/fetch_feeds.py がエピソード一覧（題名・日付・配信元の音声 URL）を app/data/feeds/ に保存し、GitHub Actions が毎日 06:00（日本時間）に更新して公開する。音声そのものは保存・再配布せず、再生時に配信元から直接受け取る（そのため再生時に端末が配信元に接続し、オフラインでは聞けない）。実際に再生した時間を数えて多聴の記録にする。
- VOA の配信は 2025 年 3 月で止まっている（それまでの回は再生できる）。TED は途中に広告が入ることがある。

## 9C. シャドーイングの録音と抑揚グラフ（2026-10-12 追加）

- 録音方式を MediaRecorder から Web Audio API（マイクの生の音を受け取り WAV にする）に変更（app/recorder.js）。理由：iPhone で自分の声が録音されない報告。ブラウザごとの録音形式の違いに左右されず、録音中の音量表示と、録音後の無音判定（最大音量 1% 未満）ができる。無音の場合は原因の候補（マイクの許可、Bluetooth イヤホン、お手本再生中のマイク停止）を表示し、お手本なしの「マイクのテスト」で切り分けられるようにした。iPhone 実機での原因の確定はユーザーの確認待ち。
- 抑揚グラフ（app/pitch.js）：お手本と自分の声の高さを 10ms ごとに推定（自己相関法、70〜400Hz、オクターブ誤りの補正、50ms 未満の孤立点の除去）し、それぞれの中央値を 0 とした半音単位で重ねて表示。自分の声の遅れはお手本との重なりから推定して差し引く。「上がり下がりの向きが同じだった割合」は目安として表示。iPhone での確認（2026-10-12）を受けて、①録音時のエコー除去・雑音抑制・自動音量調整をやめてマイクの音をそのまま録音（声が加工されたように聞こえたため）、②声として扱う音量の基準を固定値から録音ごとの相対値に変更（小さい録音で自分の線が出なかったため）、③文ごとに英文とグラフを並べる表示に変更（遅れは文ごとに合わせ直す）。さらに、④録音中にお手本が聞こえなくなったため、録音の音質を「標準（通話向けの処理あり。お手本が聞こえる）」と「そのまま（声が自然。iPhone ではお手本が聞こえないことがある）」から選ぶ方式にし、標準を初期値にした。⑤単語ごとの抑揚：tools/word_prosody.py が PC 内の音声認識でお手本の各単語の時間を求め（98% の語を特定、残りは補間）、単語ごとの上がり下がり（↗↘、±1 半音）と、内容語のうち高く強く言われている語（太字）を推定して app/data/word_prosody.json に保存。スクリプトに「抑揚ガイド」として表示し、録音後は単語ごとにお手本と同じ向きか（○✗）を表示。⑥抑揚の比較：お手本と自分の声の高さの線を重ねる表示（研究・音声分析で一般的な表示）に、単語の区切りと単語名を添える。一致度は、両者の高さの線の形の相関係数（Pearson、−1〜1。0.7 以上：よく似ている、0.4〜0.7：ある程度、0.4 未満：違いが大きい）で表し、全体は文ごとの値を測定点数で重み付けして平均する。いずれも TTS 音声からの自動推定であり、発音の正解を示すものではない。根拠：声の高さを画面に表示する練習で外国語の抑揚が改善したという報告（Hardison 2004、発話の研究。聞き取りへの効果は間接的）。

## 10. 公開方法と個人情報保護

### 10.1 公開方法：GitHub Pages（決定）

| 項目 | 内容 |
|---|---|
| サービス | GitHub Pages（無料プラン） |
| リポジトリ | 公開（Public）。無料プランでは非公開リポジトリから Pages を公開できないため |
| URL | `https://<ユーザー名>.github.io/<リポジトリ名>/`（HTTPS は自動で有効） |
| 制限（目安） | サイト全体 1GB まで、転送量 月100GB 程度、1ファイル 100MB まで |
| 公開範囲 | URL を知っていれば誰でも利用・閲覧できる。ソースコード・音声・教材も誰でも見られる |

**検討して採用しなかった案**
- Google Apps Script：Google側の枠（iframe）内で表示されるため、PWA としてのインストールやオフライン利用ができない。大量の音声ファイルの配信に向かない（既知の情報に基づく）。
- Cloudflare Pages / Netlify：非公開リポジトリでも無料で使えるが、今回は GitHub を使う方針とした。ソースコードを非公開にしたくなった場合の代わりの候補とする。

### 10.2 個人情報保護

**基本方針**
- アプリは個人情報を収集しない。学習記録・録音はスマホの中だけに保存し、外部へ送らない。
- 公開するのは、アプリ本体（HTML / CSS / JavaScript）、音声、教材、ライセンス表記だけとする。

**対策**

| # | リスク | 対策 | 担当 |
|---|---|---|---|
| 1 | Git の記録（commit）に本名やメールアドレスが残り、公開される | GitHub の設定で「Keep my email addresses private」と「Block command line pushes that expose my email」を有効にする。Git の作成者情報は GitHub の非公開用アドレス（`xxxx@users.noreply.github.com`）とニックネームにする。**最初の commit の前に設定を確認する** | ユーザー（設定）／Claude（確認） |
| 2 | 公開しないファイルをうっかり上げてしまう | `.gitignore` で除外する（メモ、`.env`、音声生成用の作業ファイル、書き出した学習データなど）。**push の前に、上げるファイルの一覧をユーザーに示して承認を得る** | Claude |
| 3 | ユーザー名から本人が特定される | 本名を含まないユーザー名にする | ユーザー |
| 4 | アカウントが乗っ取られ、サイトを書き換えられる | 二段階認証を設定する | ユーザー |
| 5 | アプリから第三者へ通信が発生する | アクセス解析・広告・外部 CDN・外部フォントを使わない。必要なファイルはすべてリポジトリ内に置く | Claude |
| 6 | スマホ内の学習記録・録音を他人に見られる | 端末のロックは利用者が行う。書き出したデータは扱いに注意するよう、アプリ内に表示する | ユーザー |
| 7 | 音声などのファイルに、作成者の情報が埋め込まれる | 生成した音声ファイルにメタデータ（作成者名など）を含めない | Claude |

**Git 操作のルール**
- `git commit` / `git push` などの Git 操作は、毎回ユーザーの許可を得てから行う。
